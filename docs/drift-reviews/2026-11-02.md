## Ranked findings

### 1. A set with a custom `--root` is still read from a different sidecar by the app than by the CLI and MCP tools (needs design)
- *Evidence:* unchanged since the last review. `set::resolve_root` honours `SetFile.root` (`src/set.rs:141`); `location::folio_path` and `ffi.rs:87` use `detect_root` only, and the MCP file tools call `location::folio_path` (`mcp.rs:382, 408, 451, 470`) while `set_list` reports the custom-root path (`mcp.rs:489`). `SKILL.md:242` still documents the exception.
- *Impact:* an agent following the set's reported sidecar and one using the tools write to two files; the human sees one. Every new entry point (the Windows client in [#104](https://github.com/johannilsson/folio/pull/104) is one) has to know the exception.
- *Direction:* decide whether a custom root is a feature. If yes, one file→root lookup in `location.rs` that consults sets, used by CLI, FFI and MCP; if no, drop `--root` and `SetFile.root`. Needs a decision, and changes the set file format and the skill. Now in its third review.

### 2. `mcp.rs` holds the protocol, the annotation tools and the client-config writers in one file (needs design)
- *Evidence:* 1297 lines; about 800 of code. Protocol and dispatch (`serve`, `handle`, `call`, lines 86-320), file tools that repeat the same sequence as the CLI (`annotate`, `reply`, `list_annotations`, 375-500), app-facing tools (`windows`, `reveal`, 519-600), and the config editors for Claude Desktop and Codex (`connect_claude`, `connect_codex`, `replace_file`, 610-760). It changed in 6 commits in the window, including the opt-in change this week ([#105](https://github.com/johannilsson/folio/pull/105)). `annotate` (399-446) and `commands/annotate.rs:20-60` still each do validate → build → anchor-check → create dir → save; only the construction was shared.
- *Impact:* each new tool or opt-in rule edits the one file that also contains unrelated config-file code, and the CLI and MCP can diverge in validation (they already word the same anchor failure differently).
- *Direction:* split into `mcp/` modules (protocol, tools, connect) and give the engine one `add_annotations(sidecar, content, items)` that both CLI and MCP call. Not urgent; the file is tested, but it is the likeliest place for the next change to go wrong.

### 3. The self-test is the largest module and still cannot run without a desktop session (needs design)
- *Evidence:* `macos/Sources/Folio/SelfTest/` is 2853 lines (was 2800), 3 files touched since the last review. FolioKit has 6 test files; `SelfTest+Scrolling.swift` and parts of `+Preview` still check layout fractions and placement.
- *Impact:* each UI change edits a long, timing-sensitive file whose failures appear only in macOS CI.
- *Direction:* as before, move layout and state rules into FolioKit unit tests and keep the self-test for wiring. Track as the extraction continues.

### 4. The sidebar badge parses the sidecar by hand (small → [#107](https://github.com/johannilsson/folio/issues/107))
- *Evidence:* `Document.pendingCount()` (`Document.swift:80`) uses `JSONSerialization` and its own "not resolved" rule, while `Sidecar.parse` (`AnnotationModel.swift:89`) and `AnnotationStore.pending` exist. Called per file on every sidebar refresh (`SidebarViewController.swift:130`). Listed as minor drift last review.
- *Impact:* a second, untested reader of the format; the badge and the window's count can disagree when "pending" changes.
- *Direction:* parse through FolioKit and count with the shared rule.
