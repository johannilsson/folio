## Ranked findings

### 1. The rest of the `folio://` link rules are still written in both Rust and Swift (needs design → [#133](https://github.com/johannilsson/folio/issues/133); parsing is a small first step → [#148](https://github.com/johannilsson/folio/issues/148))

*Evidence:* [#140](https://github.com/johannilsson/folio/pull/140) moved the reference finder into the engine (`folio_references` in `src/ffi.rs:186`, `WikiReferences.find` now calls `Rust.references`). What is left in two languages:

| What | Rust (`src/wiki.rs`) | Swift |
|---|---|---|
| Parsing | `FolioLink::parse` (:296) | `FolioLink.init` (`FolioKit/FolioLink.swift:25`) |
| Resolution | `resolve` (:340) | `resolve(among:)` (:74) |
| Does the link name this file | `points_to` (:316) | `points(to:)` (:86) |
| Is the target there | `target_found` (:358) | `targetFound` (:98) |
| Why a link is dead | `dead_reason` (:376) | `AppServer.deadReason` (`AppServer.swift:192`) with `FolioLink.message` (:125) |

The differences named last week remain: the app says "<repo> isn't in an open set" and "That file isn't here" where `folio refs --dead` says "<repo> isn't in the set" and "<name> isn't there any more", and `points(to:)` resolves symlinks while `points_to` does not.

New this week: `Rust.references` (`Rust.swift:44`) gets each link already parsed from the engine (the `Reference` JSON carries the flattened `FolioLink`), then throws that away and parses `url` again with `URL(string:)` and `FolioLink.init`. A link the engine accepts and the Swift parser rejects is silently dropped from the backlinks, so the two can still disagree about what a page links to.

*Impact:* the agent's `folio refs --dead` and the reviewer's greyed links can disagree. A new link kind or query field still has to be added twice. This is engine logic written again in Swift, and a decision (the dead reason) made in the app layer, both of which CLAUDE.md rules out.

*Direction:* as last week, and [#140](https://github.com/johannilsson/folio/pull/140) shows the shape works: the fence rules changed twice since and the app followed for free. Next, build `FolioLink` from the engine's parsed fields (and expose `FolioLink::parse` for the app's other call sites), [#148](https://github.com/johannilsson/folio/issues/148). The open design question is unchanged: `dead_reason` reads the disk and takes the open files as `Here`; the app needs to pass its open checkouts in one shape.

### 2. A set with a custom `--root` is still read from a different sidecar by the app than by the CLI and MCP tools (needs design → [#134](https://github.com/johannilsson/folio/issues/134))

*Evidence:* unchanged. `set::resolve_root` honours `SetFile.root` (`src/set.rs:192`); `location::folio_path` (`location.rs:20`), `ffi.rs:85`, `wiki::Here::of` and `target_found` use `detect_root` only. `SKILL.md:249` still documents the exception.

*Impact:* links to annotations of a custom-root file are reported dead by `folio refs --dead`, and every new entry point has to know the exception.

*Direction:* decide whether a custom root is a feature. If it is, one file→root lookup in `location.rs` that consults sets; if not, drop `--root` and `SetFile.root`. Sixth review.

### 3. MCP `annotate` still builds, anchors and saves annotations beside the CLI's path (needs design → [#135](https://github.com/johannilsson/folio/issues/135))

*Evidence:* `src/mcp.rs` is 1536 lines, unchanged. Validation is shared (`validate_fields`, imported at `mcp.rs:9`), which is why the open [#145](https://github.com/johannilsson/folio/pull/145) fixes both paths with one change. Building the annotation, the anchor check (`mcp.rs:527`) and the save (`mcp.rs:548`) are still done separately from `commands/annotate.rs::run`.

*Impact:* a rule about how annotations are built or written (as opposed to validated) still has to be added in two places.

*Direction:* unchanged: a shared `add_annotations(sidecar, content, items)` the CLI also calls; split `mcp/` into protocol, tools and connect when it is next touched.

### 4. Rule checks still live in the self-test (needs design → [#137](https://github.com/johannilsson/folio/issues/137))

*Evidence:* `SelfTest/` is 3945 lines (+32, from [#138](https://github.com/johannilsson/folio/pull/138)). [#138](https://github.com/johannilsson/folio/pull/138) put its rule in FolioKit with `NavigationHistoryTests`, and keeps only wiring in `SelfTest+Wiki.swift`, the direction this finding asks for. The wiki scenarios still carry checks that depend on the duplicated link rules of finding 1.

*Impact:* UI changes still edit long, timing-sensitive scenarios whose failures only show in macOS CI.

*Direction:* unchanged; once finding 1 is settled, move the link-rule cases into `wiki.rs` tests.

### 5. Inline-card room is still state kept beside the text in each surface (needs design → [#136](https://github.com/johannilsson/folio/issues/136))

*Evidence:* unchanged. `setInlineRoom` is written twice (`SourceEditorView.swift:366`, `PreviewView.swift:587`) behind `AnnotationSurface.swift:83`.

*Impact:* each new way for the text to change under the map (wiki pages following edits without a reload) needs its own shift.

*Direction:* unchanged: derive the room from anchors and heights on each layout, or give it one owner.
