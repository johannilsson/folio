## Ranked findings

### 1. A set with a custom `--root` is read from a different sidecar by the app and by the CLI and MCP tools (needs design)
- *Evidence:* sets store an optional `root` and `set::describe` / `resolve_root` use it (`src/set.rs:151-169`), so the app's set windows open `<custom root>/.folio/…`. The per-file entry points all use `detect_root` only: `commands::folio_path` (`src/commands/mod.rs:28-31`), `ffi.rs:84-86` (`Rust.sidecarPath`, used by single-file windows), and every MCP file tool (`mcp.rs:353, 379, 438, 457`). The skill documents this as "the one exception" (`SKILL.md:242`). It now also shows up in the MCP server: `set_list` reports the custom-root sidecar (`mcp.rs:476`) while `annotate`, `reply` and `list_annotations` on that same file write to the git-root one.
- *Impact:* an agent following a set's reported sidecar and an agent using the tools end up in two files, and the human only sees one. The rule "every entry point finds the same sidecar" (comment on `folio_path`) is false for this case, and each new entry point has to remember the exception.
- *Direction:* decide whether a custom root is a real feature. If yes, a file→root lookup that the CLI, FFI and MCP all call (consulting sets for the file); if no, drop `--root` and `SetFile.root`. This changes the set file format and the skill, so it needs a decision first.

### 2. The resolution outcome (`resolved_as`) is an untyped string and the three writers disagree on comments (small → [#23](https://github.com/johannilsson/folio/issues/23))
- *Evidence:* still `Option<String>` (`sidecar.rs:72`). `edit.rs:73-75` records a resolved comment as `dismissed` and anything else as `rejected`; `commands/accept.rs:116` records `accepted` for every kind; `commands/reject.rs:48` records `rejected` for every kind, comments included. The spec lists `resolved` as a value that nothing writes.
- *Impact:* the same human decision reads differently depending on whether the button or `folio reject` made it, and agents are told to read resolved annotations to continue a review. A compile-time type would also make the spec table checkable.
- *Direction:* a `ResolvedAs` enum and one (kind, accept/reject) function used by the three writers. Matching the app's behaviour is the least disruptive mapping. Issue #23 has the current locations.

### 3. A new annotation is built in three places (small → [#86](https://github.com/johannilsson/folio/issues/86))
- *Evidence:* `commands/annotate.rs:34-65`, `mcp.rs:388-420` and `edit.rs:85-100` each carry the unique-id loop and a 13-field `Annotation { … }` literal. The CLI and MCP validate fields and check the anchor; `AddComment` does neither (the app anchors from a selection).
- *Impact:* the sidecar is the contract between agents and the app. A new field or default has to be added three times, and the forgotten writer produces sidecars the others read differently.
- *Direction:* one constructor next to `Annotation` and one id-collision helper in `sidecar.rs`, used by all three.

### 4. The self-test is the largest and fastest-changing module, and it can only run with a desktop session (needs design)
- *Evidence:* `macos/Sources/Folio/SelfTest/` is 2800 lines (`SelfTest+Preview`, `+Source`, `+Annotations`, `+MCP` each 300–490) and was touched in 31 commits in 60 days, more than any other area. CLAUDE.md already says logic and layout rules belong in FolioKit unit tests (principle 8), and FolioKit exists now (5 test files, ~1000 lines), but wiring checks still cover rules such as scrolling fractions and card placement (`SelfTest+Scrolling.swift`).
- *Impact:* each UI change edits a long, timing-sensitive test file (#58, #66 were both fixes to flaky waits), and a failure only appears in macOS CI.
- *Direction:* as the FolioKit extraction continues, move the layout and state rules from the self-test into unit tests and keep the self-test for wiring. No single fix; track it as the extraction proceeds.
