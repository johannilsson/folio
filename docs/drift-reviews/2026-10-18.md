## Ranked findings

### 1. The page saves the whole sidecar from its own copy, which can drop an agent's concurrent writes (needs design)
- *Evidence:* every editor mutation (`resolveAnnotation`, `addCommentAnnotation`, `submitReplyRaw`, `setAnnotationComment` in `frontend/src/annotations.ts` / `raw-annotations.ts`) builds a new `Sidecar` from the module-level `currentSidecar` and calls `putFolio`, which replaces the file (`server.rs:172`, `Bridge.swift` `putFolio`). The page only learns about an agent's append on `folio:changed`, after a 300 ms poll and a 500 ms debounce (`watcher.rs`), or after the app's 300 ms poller (`Document.swift:80`). `folio annotate`/`accept`/`reject` also load, modify and save without a lock.
- *Impact:* the README pitches live review while the agent works. A click inside that window silently deletes the agent's new annotations or replies. Every new editor action adds another whole-file writer, so the race grows with the feature set.
- *Direction:* make writes per operation (resolve, reply, add, edit) and apply them server-side or in the Rust library against the file as it is on disk, the way `/api/accept` already works. Or add a revision check (ETag/mtime) to the PUT and merge by id. Either way the bridge contract changes, so `Bridge.swift`, `e2e/fixtures.ts` and `BRIDGE.md` all change.

### 2. Editor sidecar writes skip the validated, atomic save (small → [#22](https://github.com/johannilsson/folio/issues/22))
- *Evidence:* [#6](https://github.com/johannilsson/folio/issues/6) (`dd41914`) made `Sidecar::save` atomic. `put_folio` (`server.rs:172`, `tokio::fs::write`) and `Document.writeSidecar` (`Document.swift:60`, `Data.write` without `.atomic`) still write unparsed bodies in place. Only the CLI and `/api/accept` get the guarantee.
- *Impact:* the watchers can read torn files, and a malformed body breaks every later `Sidecar::load`. Any change to how saving works has to be made three times.
- *Direction:* parse into `Sidecar` and call `save()` on the server; go through Rust (or `.atomic` plus a parse check) in the app.

### 3. The annotation UI is written twice, once per editor mode (needs design)
- *Evidence:* `annotations.ts` (1309 lines) and `raw-annotations.ts` (708 lines) each have their own gutter card builder (`makeGutterCard` / `makeRawGutterCard`), card layout, overlay, comment floater, focus handling, reply submit and accept. Accept differs in mechanism. Preview calls Rust through `/api/accept` (one server-side read-patch-save). Source mode patches CM6 itself and then sends `putFile` and `putFolio` as two separate writes (`raw-annotations.ts:445`). Recent features had to land in both files: `bbe7375` (toast/flash) and `6b29a1c` (comment button placement). Both modules keep their state in module-level variables, so most of this is only reachable through Playwright.
- *Impact:* each card or overlay change costs double and is easy to miss in one mode. The source-mode accept path can leave the file patched but the annotation still pending if the second write fails.
- *Direction:* extract the mode-independent parts (card DOM, overlay, floater, thread) behind a small adapter interface (anchor → screen rect, apply edit, resolve). Then decide whether source-mode accept should go through `/api/accept` like the preview, or stay client-side so CM6 undo keeps working. That trade-off is the design question.

### 4. The resolution outcome (`resolved_as`) is an untyped string, and its values depend on which path resolved it (small → [#23](https://github.com/johannilsson/folio/issues/23))
- *Evidence:* `String` in `sidecar.rs:72` and `api.ts:111`. A comment is recorded as `dismissed` by the card button, `accepted` by Ctrl+Enter in the preview (`annotations.ts:964`) and by `folio accept`, and `rejected` by `folio reject`. The spec lists `resolved`, which nothing writes, and says highlights behave like comments, but they are recorded as `accepted`.
- *Impact:* agents that read outcomes to continue a review get different answers for the same decision, and no type stops new call sites from adding a fifth value.
- *Direction:* one enum and one kind → outcome mapping shared by the CLI and the editor; correct the spec table.

### 5. A set with a custom `--root` reads a different sidecar from the one the per-file CLI writes (needs design)
- *Evidence:* `commands::folio_path` (`src/commands/mod.rs:27`) always uses `detect_root`. Sets use `resolve_root`, which prefers the stored `root` (`src/set.rs:151`). The skill has to document the gap as an exception (`.claude/skills/folio/SKILL.md:236`). That steers agents away from `folio annotate`'s validation and onto hand-written JSON.
- *Impact:* the spec's promise that "the CLI, the server and the macOS app all use this rule" is false for these sets. Any new per-file command repeats the gap. An agent that follows `folio check` writes annotations the set never shows.
- *Direction:* either have the per-file commands look up a containing set's root, or store the root next to the files (for example a `.folio/` marker) so the location follows from the file alone. Then drop the exception from the skill.
