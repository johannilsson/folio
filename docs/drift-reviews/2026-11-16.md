## Ranked findings

### 1. `folio://` links are parsed, resolved and checked twice, in Rust and in Swift, and the two already differ (needs design; the reference finder is small → [#131](https://github.com/johannilsson/folio/issues/131))

*Evidence:* [#118](https://github.com/johannilsson/folio/pull/118) and [#122](https://github.com/johannilsson/folio/pull/122) wrote the link rules in both languages:

| What | Rust (`src/wiki.rs`: `folio refs`, `folio relink`, MCP) | Swift (app) |
|---|---|---|
| Parsing | `FolioLink::parse` (:264) | `FolioLink.init` (`FolioKit/FolioLink.swift:25`) |
| Resolution | `resolve` (:312) | `FolioLink.resolve(among:)` (:74) |
| Does the link name this file | `points_to` | `points(to:)` |
| Is the target there | `target_found` (:330) | `targetFound` (:98) |
| Why a link is dead | `dead_reason` (:348) | `AppServer.deadReason` (`AppServer.swift:192`), a decision made in the UI layer |
| A page's links | `references` (:418) | `WikiReferences.find` (`WikiReferences.swift:35`) |

The Rust doc comments say "as `FolioLink.resolve(among:)` in the app" and "the same reasons the app greys a link with". Nothing tests that this is true, and it already isn't:
- `references` skips links inside a fenced code block. `WikiReferences.find` only skips headings there, so the app counts a backlink that `folio refs` does not.
- Rust says "<repo> isn't in the set" and "<name> isn't there any more". The app says "<repo> isn't in an open set" and "That file isn't here".
- `points(to:)` resolves symlinks. `points_to` does not.

Open items, by contrast, go through the engine (`folio_open_items`, `folio_tick_item`).

*Impact:* the agent's `folio refs --dead` and the reviewer's greyed links can disagree about the same page. Every change to the link format, such as a new link kind or a new query field, has to be made twice by hand. This is the pattern CLAUDE.md rules out ("never reimplement them in Swift", "the UI applies decisions, does not make them").

*Direction:* expose `wiki::references`, `FolioLink::parse` / `resolve` and `dead_reason` through `ffi.rs`, the way open items already are, and make the FolioKit types thin wrappers. `dead_reason` reads the disk and takes the open files as `Here`. The app would pass its open checkouts in, and the call needs one shape for "what is open". The reference finder alone is a small first step ([#131](https://github.com/johannilsson/folio/issues/131)).

### 2. A set with a custom `--root` is still read from a different sidecar by the app than by the CLI and MCP tools (needs design)

*Evidence:* unchanged.
- `set::resolve_root` honours `SetFile.root` (`src/set.rs:192`).
- `location::folio_path` (`location.rs:22`) and `ffi.rs` use `detect_root` only.
- Wiki mode adds two more readers that ignore the set's root: `wiki::Here::of` (`wiki.rs:257`) and `target_found`, which reads `location::folio_path`.
- `SKILL.md:249` still documents the exception.

*Impact:* links to annotations of a custom-root file are reported dead by `folio refs --dead`. Each new entry point has to know the exception. Set files went to version 2 this week without settling it.

*Direction:* decide whether a custom root is a feature. If it is, add one file→root lookup in `location.rs` that consults sets. If not, drop `--root` and `SetFile.root`. Fifth review.

### 3. `mcp.rs` keeps growing, and `annotate` still differs from `commands/annotate.rs` (needs design)

*Evidence:* 1536 lines (+239 this week), 49 functions. The new tools are the right shape: `items`, `refs`, `relink` and `link` are four-line wrappers over `commands::*::find` / `build` / `repair`. `annotate` (`mcp.rs`) still does validate → build → anchor check → create dir → save itself, beside `commands/annotate.rs::run`.

*Impact:* a new annotation rule, like an opt-in field or a validation, has to be added in two places. The protocol, the tools and the client-config writers all edit the same file.

*Direction:* move `annotate` onto a shared `add_annotations(sidecar, content, items)` the CLI also calls, as `annotations_since` did with `changes.rs`. Split `mcp/` into protocol, tools and connect when it is next touched.

### 4. The self-test grew by 851 lines in a week (needs design)

*Evidence:* `SelfTest/` is 3913 lines (was 3062). `SelfTest+Wiki.swift` alone is 817. FolioKit's test files doubled (6 → 12: `FolioLinkTests`, `WikiLinksTests`, `WikiReferencesTests`, `OpenListTests`, `FileReferencesTests`, `SidebarTreeTests`), which is the right direction. But the wiki scenarios (`backlinkScenario`, `worktreeScenario`) still carry checks that depend on the duplicated rules of finding 1.

*Impact:* UI changes edit long, timing-sensitive scenarios whose failures only show in macOS CI.

*Direction:* as before. Once finding 1 moves the link rules into Rust, their cases belong in `wiki.rs` tests, and the self-test can keep only the wiring.

### 5. Inline-card room is still state kept beside the text in each surface (needs design)

*Evidence:* [#116](https://github.com/johannilsson/folio/pull/116) fixed the scroll jump by keeping the room on reload and shifting it with suggestion previews (`PreviewView.swift`, `SourceEditorView.swift`). `InlineRoom` (`TextSurface.swift:234`) is still owned once per surface, with `setInlineRoom` written twice (`SourceEditorView.swift:366`, `PreviewView.swift:587`). The fix has no self-test check for the scroll offset after an outside change.

*Impact:* wiki pages that follow edits without a reload are a new way for the text to change under the map.

*Direction:* unchanged. Derive the room from anchors and heights on each layout, or give it one owner with a single `textChanged(map)` entry.
